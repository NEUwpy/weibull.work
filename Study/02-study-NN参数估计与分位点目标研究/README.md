# Study 02：面向寿命分位点目标的 NN Weibull 参数估计研究

> 创建日期：2026-07-11
> 当前状态：R12 准备工作已收口；可申请一个全新的 A-E1 formal training/validation 授权，但尚未授权或启动；test 继续 sealed。

## 目录定位

本目录承载 Study/02 的研究设计、前置研究、正式实验、证据和论文材料。当前唯一论文主线暂定为：

> 比较两条分别优化的估计路线：一条先用 NN 估计三参数 Weibull 分布，再间接计算目标寿命分位点；另一条用 NN 直接估计目标寿命分位点。如果工程上只需要 \(x_{0.95}\)，保留完整 Weibull 参数化究竟付出了多少分位点精度代价？

这里的研究目的不是为了使用神经网络，而是从可靠性工程最终关心的寿命分位点出发，检验训练目标与工程目标对齐后能否产生可量化、可泛化且边界清楚的收益。

本文统一采用可靠度分位点记号：

\[
x_R=F^{-1}(1-R)=\gamma+\eta[-\ln(R)]^{1/\beta}.
\]

因此，\(x_{0.95}\) 表示可靠度仍为 95% 时的寿命，等价于失效分布的下侧 5% 分位点，不是通常统计记号中的第 95 百分位。

## 当前研究结构

### 前置研究：NN 直接参数估计基础

该部分是进入主研究前的积累和方案冻结依据，不预设为独立论文。它需要澄清既有 NN Weibull 参数估计研究中尚未充分回答的问题，例如：

- 为什么使用样本统计特征训练；直接输入样本值会怎样？
- NN 与传统参数估计方法如何公平比较？
- 模型在参数范围、样本量和未见组合上的泛化能力如何？
- 哪些输入特征、网络结构和训练设置真正有贡献？

前置研究的范围由既有 NN Weibull 参数估计论文留下、且会阻碍主研究继续推进的具体疑问决定。它需要对这些疑问形成证据化回答，并由此为主研究提供可复用的输入表示、基线模型、训练协议和比较口径。它形成研究积累，但是否具备独立发表价值留待证据形成后判断。

### 主研究：面向寿命分位点的目标转换

主研究比较参数精度目标与寿命分位点目标，并至少回答：

- 目标分位点的样本外预测精度能改善多少？
- 改善是否跨参数区域、样本量和数据条件成立？
- 参数估计精度及非目标分位点是否付出代价？
- 直接预测参数后计算分位点，与直接预测分位点相比如何？
- 主研究自身需要哪些消融、泛化和稳健性验证？

前置研究不能替代主研究自身的消融与泛化实验；它只负责减少基础方案的不确定性。

当前只聚焦 \(x_{0.95}\)（B5 寿命）作为训练目标和主要论文结论，不同时训练 \(x_{0.90}\) 或 \(x_{0.99}\)。后续可将非目标可靠度点作为跨分位点泛化检查，例如评价按 \(x_{0.95}\) 训练的模型在 \(x_{0.99}\) 上偏差多大；这不属于当前核心训练任务。

当前核心比较是两条完整估计路线：

1. **参数路线**：NN 输出 \((\beta,\eta,\gamma)\)，以参数估计准确性为训练目标，再由预测参数计算 \(x_{0.95}\)。
2. **工程目标路线**：NN 直接输出 \(x_{0.95}\)，以该分位点的估计准确性为训练目标。

核心问题是：如果工程上只需要 \(x_{0.95}\)，保留完整 Weibull 参数化究竟付出了多少分位点精度代价？

两条路线采用双层比较，但优先级如下：主分析允许参数路线和直接分位点路线在合理且对等的资源预算下分别优化，比较各自可达到的实际最佳 \(x_{0.95}\) 表现；相同数据、相同输入和相同模型骨干的严格受控比较放在后续验证中，用于辅助解释差距来源。

## 环境与复现入口

Study/02 正式代码（`code/study02a/*.py`）依赖 PyTorch。为避免依赖某一台机器的隐含环境，可复现依赖声明在本目录的 `requirements.txt`：

```
pip install -r "Study/02-study-NN参数估计与分位点目标研究/requirements.txt"
```

它通过 `--extra-index-url` 拉取 CPU 版 torch，并 pin 了验证过的 numpy/scipy/pandas 版本（2026-07-17）。

冻结工件的字节哈希（`configs/A-g2-protocol-v1.json`、`configs/A-g2-search-v1.json`、`configs/A-g3-pilot-amendment-v4.json`、`artifacts/pilot/G3-matrix/experiment_matrix.csv`）按 LF 内容批准。仓库根的 `.gitattributes` 对这些文本类型强制 `eol=lf`，因此即使在 Windows 默认 `core.autocrlf=true` 上做全新 checkout，工作树也是 LF，`verify_frozen_hashes` / `FROZEN_MATRIX_SHA256` 无需人工改 Git 配置或手工重写文件即可通过。
