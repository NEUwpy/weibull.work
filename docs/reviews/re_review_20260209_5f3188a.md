我针对 review 中提到的问题进行以下阐释和规划：

## 1. 关于“方法空壳”问题 (Problem 1)

**回应**:
因为我需要找到每个方法的针对性的论文，所以方法进度慢。事实上，这个事情不能一蹴而就的。因此还需要一段时间慢慢完善。
基本上我的工作流是：
1. 找到对应的文献。
2. 传到文献库。
3. 根据文献来编写 Python 程序。
4. 决定过程展示结果展示之类的。

这才算是一个方法。

**处理策略**:
- 严格遵循“所见即所得”。
- 未实现的方法在 UI 上显示为不可选或“待实现”，杜绝使用 fallback 算法欺骗用户。
- 只有当我真正完成了上述 4 步工作流后，才开放该方法的使用。

## 2. 关于“后端协议不统一”问题 (Problem 2)

**回应**:
这个我确实没注意，应该怎么弄呢？确实应该弄好这样才能保证所有的方法都能正常应。

**处理策略**:
- **短期内强制统一**：定义一个标准的后端返回信封 (Envelope)。
- 即使这需要修改现有的所有算法代码，也必须现在做，长痛不如短痛，消除架构隐患。

## 3. 关于“前后端职责边界”问题 (Problem 3)

**回应**:
我还是想计算只依靠后端，现在这个前端方法的残留我需要能够找方法避免对实际运用的方法的影响。

**处理策略**:
- **彻底剥离**：前端 `src/lib/weibull.ts` 中用于参数估计的逻辑将被移除或标记为废弃。
- 前端只保留**渲染逻辑**（如根据参数画 PDF/CDF 曲线），不保留任何**计算逻辑**（如根据数据反推参数）。

## 4. 关于“自动化测试”问题 (Problem 4)

**回应**:
自动化测试确实是需要，应该怎么弄呢？

**处理策略**:
- **纳入计划但暂缓执行**：目前优先处理协议统一和方法实现，测试套件作为下一步计划，待核心架构稳定后引入。

## 5. 关于“案例库”和“数据模型”问题 (Problem 5)

**回应**:
这个就涉及到对案例库的改造了，案例库现在没有详情页，现有的两个其实是从 2，1000，1000 里抽样出来的。随着文献增多，肯定也有更多的真实数据的。
因此案例库肯定是��很大的改动空间。

**处理策略**:
- **提前升级数据结构**：虽然案例尚少，但现在就定义好支持删失 (Censored) 和区间 (Interval) 数据的底层结构。
- 防止未来数据量大时面临痛苦的迁移工作。

## 6. 未来构想与愿景

1.  **完善现状**: 把目前的弄完善，不要给后续留下架构上的、设计上的隐患。
2.  **稳步丰富**: 丰富方法，但是也要能做到给我慢慢丰富方法的时间和空间。
3.  **全流程打通**: 一方面要能跑通可靠性分析全流程。
4.  **AI 赋能**: 一方面要能做到利用人工智能方法优化参数估计方法（利用智能优化算法和神经网络等）。
    - **形态确认**: AI 不做为独立方法（如 "AI方法"），而是作为传统方法的**幕后优化器 (Optimizer)** 存在（如 "MLE (with PSO Optimization)"）。

**最终目标**:
既是简单的而又全面强大的威布尔计算器，又是有案例、有文献、有方法支撑的可靠性分析平台，又是一个利用各种人工智能方法对传统参数估计方法创新的快速实现并可视化的平台。

## 7. 详细行动规划 (Detailed Action Plan)

### 7.1 架构重构 (Architecture Refactoring)

#### A. 后端协议标准化 (The Envelope)
在 `python/main.py` 中定义统一响应模型，替代目前的 Tuple 返回。

```python
class EstimationResult(BaseModel):
    method_slug: str          # 方法ID (e.g., "mle")
    params: Dict[str, float]  # 核心参数 {"beta": 2.5, "eta": 100, "gamma": 0}
    metrics: Dict[str, float] # 统计指标 {"r_squared": 0.99, "aic": 120.5}
    status: str               # "converged" | "failed" | "max_iter"
    trace: Optional[Dict]     # 可视化追踪数据
    error_msg: Optional[str]  # 错误信息
```

#### B. 前端逻辑清理
- 修改 `src/lib/weibull.ts`:
  - 保留: `generatePDFPoints`, `generateCDFPoints`, `calculateMedianRanks` (绘图用)
  - 移除/废弃: `calculateWeibullParameters` (参数估计用)
- 确保所有计算请求走 `/api/calculate`。

#### C. 方法可见性管理
- 修改 `src/data/methods.json`:
  - 为每个方法节点添加 `status` 字段: `"implemented" | "planning"`
  - 前端渲染 MethodSelector 时，若 `status === "planning"`，则置灰不可点，提示"文献研读中"。

### 7.2 数据模型升级 (Data Model Upgrade)

定义通用的可靠性数据结构，用于 Python 后端和 Case JSON。

```json
// New Case Format
{
  "id": "case_001",
  "title": "Aero Engine Turbine Blade",
  "type": "reliability_data",
  "data": [
    { "value": 100, "status": "F", "count": 1 },  // Failure
    { "value": 150, "status": "S", "count": 5 },  // Suspension (Right Censored)
    { "lower": 50, "upper": 60, "status": "I", "count": 2 } // Interval Censored
  ]
}
```

### 7.3 AI 增强路径 (AI Enhancement Path)

将 AI 从 `methods/ai.py` 移动/重构为 `optimizers/` 模块。

- **Current**: Method = `AI_PSO` -> Run PSO logic.
- **Future**: Method = `MLE` -> `mle.run(optimizer="pso")`.
- **UI**: 在计算卡片背面或高级设置中增加 "Optimizer Strategy" 下拉框。

### 9.2 当前系统问题诊断

#### 问题 1: 方法实现状态不透明
**现状**:
- 已完成（3 个）：MLE、WMLE、MDM（有后端 + 前端展示 + 文档 + 流程可视化）
- 半成品（7 个）：LRE、LSE、MM、MPS、PWM、Bayesian、Grey GM(1,1)（有 .py 文件但无文献/展示/文档）
- 前端：这些半成品方法**不可选**（已正确隐藏）

**理想状态**:
- `methods.json` 每个方法有明确的 `status` 字段：`"implemented"` | `"planning"`
- 前端根据状态渲染：不可点击 + "文献研读中"提示
- 用户看到的和实际能用的完全一致（所见即所得）

#### 问题 2: 后端协议不统一
**现状**:
- MLE 返回 `(eta, beta, gamma, bool, message)`
- WMLE 返回 `{"params": ..., "weights": ...}`
- MDM 返回自定义字典

**理想状态**:
- 所有方法返回统一的 `EstimationResult` 对象
- 前端解析逻辑统一，不需要为每个方法写特殊处理

#### 问题 3: 前端残留计算逻辑
**现状**:
- `src/lib/weibull.ts` 中仍有 `calculateWeibullParameters` 函数
- 存在用户误用的风险（虽然目前未使用）

**理想状态**:
- 前端只保留渲染逻辑（生成曲线点、计算中位秩）
- 所有参数估计强制走后端 API

#### 问题 4: AI 增强架构未定义
**现状**:
- AI 方法作为独立方法存在（如 `AI_PSO`）
- 与传统方法耦合，无法灵活组合

**理想状态**:
- 智能优化算法作为**可插拔优化器**
- 架构：`方法(数据, 优化器="scipy|pso|de|ga")`
- UI：方法选择 + 优化器选择（二级联动）

#### 问题 5: 数据模型不支持删失数据
**现状**:
- 案例 JSON 只有 `value` 字段
- 无法表达右删失（Suspension）、区间删失（Interval）

**理想状态**:
- 新数据结构支持 `status: "F|S|I"`（失效/删失/区间）
- 为未来科研需求预留能力
