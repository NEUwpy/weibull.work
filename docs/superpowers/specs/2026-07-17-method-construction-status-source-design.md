# 方法建设单一状态源设计

> 本设计约束传统参数估计方法的建设状态、页面映射和验收流程。它不改变 `Study/01`、`Study/02` 等论文研究线，也不把平台工程建设包装为论文创新。

## 1. 背景与问题

平台的方法分类主要来自 `src/content/181-004-pdf原文.md`。当前方法总览已经展示 8 个类别和 22 个叶子方法，但建设状态分散在多处：

- `05-状态.md` 维护一份人工状态表；
- `src/app/help/changelog/page.tsx` 另行硬编码功能状态看板；
- `src/data/methods.json` 的 `hasDetail` 同时承担详情状态和计算器可选状态；
- `python/methods/registry.py` 决定后端实际可执行方法。

这些来源可以互相矛盾，也无法仅通过阅读说明文档准确判断方法建设进度。本设计把 `05-状态.md` 建成传统参数估计方法建设状态的单一事实源，并用自动验证约束它与真实代码、内容和证据保持一致。

`README.md` 继续承担项目级入口和总体状态快照；`05-状态.md` 专门权威管理方法建设能力。落实本设计时应同步修订 `02-规则.md` 的文档职责表述，避免“项目总体状态”和“方法建设状态”发生权威范围冲突。

## 2. 目标

1. 只需阅读 `05-状态.md`，即可了解每个叶子方法的当前建设层级、原子状态、证据位置和阻塞原因。
2. 功能状态看板、方法详情页栏目状态和计算器开放条件使用同一份状态数据，不再分别硬编码。
3. 方法总览保持当前简洁视觉，不重复展示建设看板信息。
4. 第一层全部完成后，方法才能在计算器中公开选择。
5. 文档声明必须接受代码、文件、测试和论文证据的自动一致性检查。
6. 允许同族方法复用核心组件，但禁止只有别名而没有独立算法行为的伪实现。
7. 为 Hermes 执行、Codex 审核建立可重复的证据闸门。

## 3. 非目标

- 本设计不直接实现任何新增估计算法。
- 本设计不重新设计方法总览或计算器界面。
- 本设计不把全部公式、论文正文、流程数据和验证报告集中复制进 `05-状态.md`。
- 本设计不把“方法对比”计入单个方法的三级闭环。
- PSO、SVR、ANN 虽属于最终覆盖范围，但其训练数据、模型资产、泛化验证和在线推理标准需要独立设计，不能直接套用传统解析方法的全部验收规则。

## 4. 建设对象与共享实现

### 4.1 建设对象

建设和验收对象是方法总览中的 22 个叶子方法。8 个类别页只负责分类与介绍，不计入算法完成度。

传统方法包括：MLE、MMLE、MPS、WMLE、LSE、WLSE、MDM、EIV、LRE、BLRE、MM、PWM、LM、TLM、GM(1,1)、MVE、LSF、Gibbs、MAP。AI 方法包括 PSO、SVR、ANN，后者另设成熟度标准。

### 4.2 共享核心

同族变体可以共享样本预处理、目标函数构造、优化器、结果格式等底层组件。例如 LSE 和 WLSE 可以共享最小二乘拟合框架，但 WLSE 必须拥有自己的权重公式和执行分支。

每个叶子方法仍必须具备：

- 独立方法 ID 和计算器入口；
- 独立公式、参数规则或算法差异；
- 可区分的执行分支；
- 独立测试和基准断言；
- 独立详情说明；
- 至少一篇针对该方法的同行评议论文依据。

仅把 `run_variant` 指向另一个方法、只改显示名称，或者在失败时静默返回其他方法结果，均不算实现。

## 5. 单一事实源格式

`05-状态.md` 采用“YAML 元数据 + Markdown 说明正文”结构：

- YAML 是机器可读的唯一状态真值；
- Markdown 正文解释层级、字段、维护规则和阅读方式；
- 公式、流程、测试、论文及验证材料保存在职责对应的文件中，由 YAML 记录证据路径；
- 允许生成只读缓存或类型化中间产物，但生成物不得人工编辑，也不构成第二事实源。

每个叶子方法至少包含以下字段组：

### 5.1 身份与关系

- `id`：与方法分类数据和后端调用一致的稳定 ID；
- `name`：展示名称；
- `family`：所属方法族；
- `shared_core`：可选，共享核心模块或规范标识；
- `classification_source`：181-004 中的分类依据。

### 5.2 理论依据

- 专项论文状态；
- 论文题名、出处、年份；
- DOI 或等价的稳定标识；
- 本地文献记录或说明路径。

181-004 只作为分类和文献线索来源，不能单独充当全部方法的专项理论依据。原始提出论文优先；若原始论文确实不可得，可以使用公式完整、方法定义明确的同行评议论文替代。

### 5.3 原子建设项

第一层：

- 后端算法实现；
- 算法测试；
- 计算器接入；
- 公式及原理说明；
- 程序流程。

第二层：

- 计算过程；
- 结果分析。

第三层：

- 适用范围；
- 可信性验证。

每个原子项包含状态、证据路径和可选说明。状态枚举为：`todo`、`in_progress`、`done`、`blocked`、`not_applicable`。

约束如下：

- `done` 必须有可检查证据；
- `blocked` 必须填写阻塞原因；
- 必填建设项原则上禁止 `not_applicable`，确需例外时必须说明并经过 Codex 审核；
- 共享核心必须指向真实核心模块，同时保留本方法的独立分支和测试证据。

## 6. 自动层级推导

总体层级不得人工填写，只能由原子状态连续推导：

1. **第一层完成**：专项论文以及第一层五项全部为 `done`。
2. **计算器公开**：严格等于第一层完成。计算器接入可以在建设期间完成和测试，但第一层闭合前不得向用户开放。
3. **第二层完成**：第一层完成，且计算过程、结果分析均为 `done`。
4. **第三层完成 / 完整闭环**：前两层完成，且适用范围、可信性验证均为 `done`。

后续层可以提前施工，但总体成熟度不能跨过未闭合的前置层。例如结果分析已经完成而程序流程缺失时，该方法仍显示为第一层建设中。

“方法对比”是涉及至少两个方法的平台级能力，独立管理，不参与单方法闭环和单方法完成率。

## 7. 页面消费规则

### 7.1 功能状态看板

功能状态看板集中展示全部叶子方法的原子状态、自动层级、完成率、证据入口和阻塞原因。现有 TypeScript 硬编码状态必须移除。

### 7.2 方法总览

方法总览维持当前简洁展示，不添加显眼的建设标签，不复制功能状态看板。分类和方法介绍仍按既有职责管理。

### 7.3 方法详情页

所有栏目始终保留。未完成栏目显示 `未开始`、`进行中` 或 `受阻`，并在适用时展示原因；已完成栏目加载相应内容。详情页还应能说明专项论文依据以及共享核心关系。

### 7.4 计算器

保持当前交互和视觉：可用方法正常选择，建设中方法灰显并标注“开发中”。不重做选择器界面。

计算器是否开放不再由 `hasDetail` 决定，而由 `05-状态.md` 自动推导的第一层完成状态决定。详情页中的“在计算器中应用”遵循同一规则，并在第一层完成时正确预选所选方法。

## 8. 解析、验证与失败策略

统一解析模块负责读取 YAML、校验结构、生成类型化方法能力清单，并供各消费端使用。不得在页面中维护另一份手写状态数组。

自动验证至少包括：

- YAML 结构、版本和状态枚举合法；
- 状态文档完整覆盖方法总览中的全部叶子方法；
- 方法 ID 与分类数据一致、无重复、无多余项；
- `done` 项的证据路径存在；
- 声明后端完成的方法已注册、可调用且不是 `NotImplementedError` 占位；
- 声明测试完成的方法存在独立测试和有效断言；
- 共享核心的方法存在独立执行分支和独立测试；
- 专项论文包含可追溯题名、出处以及 DOI 或等价标识；
- 第一层未完成的方法不能在计算器中选择；
- 第一层完成的方法可以正确调用，且返回身份与用户所选方法一致；
- 算法失败不会静默回退并冒充另一个方法；
- 功能状态页面和计算器不再维护重复状态真值。

解析失败、字段缺失或状态与真实证据矛盾时采取 fail-closed：构建或测试失败，相关方法不得默认开放。

## 9. 论文缺口交接

论文材料由用户处理。Hermes 或 Codex 在建设中发现缺少合格专项论文时，不得擅自以 181-004、综述、博客或不可核验材料替代，也不继续把相关理论状态升级为完成。

执行者应停止该方法依赖论文的工作，并提交：

```text
PAPER_NEEDED
方法：<method id and name>
需要：<原始提出论文或公式完整的同行评议替代论文>
已知线索：<题名、作者、年份、DOI 或引用线索；没有则写无>
用途：<公式核对、参数规则、测试基准或理论说明>
当前可继续部分：<不依赖论文且仍可安全推进的工作>
```

用户提供论文或明确处理意见后，该方法再恢复相关建设和验收。其他互不依赖的方法可以继续推进。

## 10. Coworker 执行与审核

### 10.1 角色

- Hermes：在任务合同边界内选择实现路径，修改代码和文档，运行验证，提交证据报告；
- Codex：核对真实 diff、算法行为、论文依据、测试和状态升级，给出 `APPROVE / REVISE / BLOCK`；
- 用户：处理 `PAPER_NEEDED`，决定无法获得论文时是否更换来源或调整范围。

### 10.2 实施批次

1. 状态治理和安全基础：YAML 单一事实源、解析器、层级推导、一致性测试、看板映射、计算器门控和静默回退修复；
2. 现有方法重新验真：MLE、MMLE、WMLE、MDM、LRE；
3. 传统方法按家族分批建设：MPS；LSE/WLSE/EIV；LRE/BLRE；MM/PWM/LM/TLM；GM(1,1)；MVE/LSF；Gibbs/MAP；
4. AI 方法独立设计和施工：PSO、SVR、ANN；
5. 第二层和第三层按优先级补全；
6. 平台级方法对比独立建设。

每批必须独立报告和验收；未获 `APPROVE` 不把该批状态视为完成。不得让多个执行者在同一工作树同时修改同一组文件。

## 11. 验收标准

本设计落实完成时应满足：

- 修改一个方法状态只需编辑 `05-状态.md`，页面不再同步修改硬编码状态；
- 功能状态看板准确呈现 YAML 中的原子状态和自动层级；
- 方法总览保持当前简洁视觉；
- 计算器保持当前交互，但严格只开放第一层完成的方法；
- 方法详情页准确展示已完成内容和未完成状态；
- 文档、分类数据、后端注册、测试和证据不一致时自动验证失败；
- 任何方法失败都不会被静默包装成另一种方法的成功结果；
- 缺少专项论文时按 `PAPER_NEEDED` 交给用户处理；
- `Study/01` 等不相关研究文件不被本任务修改或提交。
