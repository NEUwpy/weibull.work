# AI 协作项目契约

> 本文档只定义 Weibull 项目内的协作红线、交付证据和验证要求。
> 多 agent 调度、执行/审查优先级、审查裁决语言和通用报告模板由 `coworker` skill 维护。

---

## 1. 适用范围

当任何 AI 助手在本项目中计划、执行或审查代码、文档、实验脚本、生成数据时，适用本文档。

职责边界：

- `coworker` skill 负责：谁是执行者、谁是审查者、是否需要二级审查、审查裁决格式。
- 本文档负责：Weibull 项目内什么不能碰、必须复用什么、必须跑哪些验证、审查时必须核对哪些项目事实。
- 用户保留最终合并、提交、上线、删除、范围扩大决策权。

---

## 2. 必读入口

进入本项目做计划、实现或审查前，按需阅读：

- `AGENTS.md`：AI 助手入口和文档路由。
- `README.md`：项目简介、技术栈、快速启动。
- `02-规则.md`：写新代码前必读，尤其是复用规则和新增流程。
- 专题规范：根据任务读取 `02-A-适用范围规范.md`、`02-B-可信性验证规范.md`、`python/studies/common/README.md`、`python/studies/mdm/README.md` 等。

禁止把 `_archive/` 当作实现参考。

---

## 3. 项目架构红线

### 3.1 通用红线

- 禁止读取 `_archive/` 作为参考。
- 写新代码前必须先查 `02-规则.md`。
- 不重复造轮子；已有通用组件、指标函数、图表组件应优先复用。
- 不把硬编码数据写进 TS/JS 文件；数据应放在 `content/` 或 `public/`。
- 中文文件必须保持 UTF-8；必要时运行 `scripts/check-encoding.ps1`。

### 3.2 后端红线

- 统计推断、参数估计、蒙特卡洛模拟属于后端职责。
- `python/main.py` 是 API 层，不应继续堆叠复杂计算逻辑。
- 方法调用应优先走 `methods.registry.resolve_method()` 和 `studies.common.runner.run_method(...)`。
- 蒙特卡洛应优先走 `python/studies/common/simulation.py` 的共享入口。
- 新增方法应保持“一方法一实现文件”：`python/methods/{method}.py`。

### 3.3 前端红线

- 前端负责 UI、交互、图表渲染，不承担核心统计推断。
- 图表优先复用 `src/components/shared/charts/` 或已有方法专用图表。
- 指标计算优先复用 `src/lib/metrics.ts`，不要在组件里内联重复实现。
- 页面文案、说明文档遵循“表里分离”：用户可见内容与开发者内部注释分清。

---

## 4. 执行交付物

执行者完成实现后，必须交付可审查证据：

- 修改文件列表。
- 实现摘要。
- 已运行验证命令和结果。
- 未运行验证命令及原因。
- 偏离计划之处；没有偏离时明确写“无”。

遇到项目事实与计划不符时，停止并报告，不要自行扩大范围或绕路。

---

## 5. 审查清单

审查者必须至少检查：

- `git diff --stat`。
- 具体 diff 是否只覆盖计划范围。
- 是否违反 `02-规则.md` 的复用原则。
- 是否违反前后端职责边界。
- 是否更新必要文档、测试或生成数据。
- 是否运行并通过与改动范围匹配的验证命令。
- 若需要审查裁决，使用 `coworker` skill 的 Review Verdict Protocol。

---

## 6. 常用验证命令

根据改动范围选择，不要求每次全部运行。

### 编码检查

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-encoding.ps1
```

期望：输出 `Encoding check passed`。

### 后端测试

```powershell
uv run --with pytest --with scipy --with fastapi --with numpy --with pydantic --with pandas python -m pytest python\tests -q
```

期望：测试通过，无失败。

### 前端构建

```powershell
npm run build
```

期望：构建通过。

### Git 空白检查

```powershell
git diff --check
```

期望：无输出。

## 7. 失败处理

如果同一实现连续两轮未通过审查，应停止继续小修小补，重新判断：

- 计划是否不够清楚？
- 任务是否需要拆分？
- 架构前提是否错误？
- 是否应由更高优先级执行者接手关键修复？

此时应向用户给出新的建议，而不是继续要求执行者盲改。
