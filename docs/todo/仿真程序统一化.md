# 仿真程序统一化

## 问题背景

项目中的蒙特卡洛仿真功能存在代码重复、架构分散、命名混乱的问题，需要统一设计。

## 当前现状

### 现有仿真入口（共 4 个）

| 类型 | 文件 | 服务 Tab |
|------|------|----------|
| 预计算脚本 | `python/studies/mle/simulate.py` | 适用范围估计 |
| 预计算脚本 | `python/studies/mdm/simulate.py` | 适用范围估计 |
| 预计算脚本 | `python/studies/wmle/simulate.py` | 适用范围估计 |
| 实时 API | `python/main.py:350` `/monte_carlo_simulate` | 方法对比 |

### 核心问题

1. **功能重复**：每个方法都有独立的 `simulate.py`，大量代码相同：
   - `parse_config()` - 解析配置
   - `get_param_values()` - 获取参数值
   - `generate_chunk_filename()` - 生成文件名
   - `generate_weibull_sample()` - 生成威布尔样本
   - `load_index()` / `save_index()` - 索引管理
   - `cmd_generate()` / `cmd_merge()` / `cmd_status()` / `cmd_clean()` - 命令处理

2. **变量名不一致**（参见 `参数命名统一化.md`）：
   - 样本量：`sampleSize` / `n` / `sample_size`
   - 偏移量：`offset` / `d` / `offset_value` / `process`
   - 不同文件中混用

3. **架构分离**：
   - 预计算脚本：批量生成 chunk 文件，存储到 `public/studies/{methodId}/chunks/`
   - 实时 API：根据请求参数即时计算，返回 JSON
   - 两套逻辑，数据格式虽一致但代码不共享

## 用户观点

> "不同的 Tab，不同的方法，目的都是：**对于 xx 方法的 xx 参数，用 xx 次数获得 xx**。应该是可以有一个通用的仿真程序，或者像是 main.py 一样是那种 API。"

核心诉求：
- 一个统一的仿真入口
- 支持不同方法（通过参数指定）
- 支持不同场景（预计算 vs 实时）
- 统一的变量命名

## 可能的改进方向

### 方案 A：统一 API 模式

废弃独立的 `simulate.py` 脚本，全部通过 API 调用：

```
POST /api/simulate
{
  "method": "mle",
  "params": { "beta": 1.5, "eta": 1000, "n": 10 },
  "rep": 1000,
  "seed": 42,
  "mode": "stream" | "batch"  // 实时返回 vs 批量生成文件
}
```

优点：
- 单一入口，易于维护
- 前端统一调用方式
- 便于添加新方法

缺点：
- 预计算场景需要额外的任务调度机制
- 文件写入权限管理

### 方案 B：通用脚本 + 配置驱动

保留脚本形式，但合并为一个通用脚本：

```bash
python simulate.py mle demo1 --generate
python simulate.py mdm demo1 --generate
python simulate.py wmle demo1 --status
```

脚本内部：
1. 读取 `public/studies/{method}/{study}/config.md`
2. 根据方法类型动态加载算法类
3. 统一的参数映射和命名

优点：
- 保持现有的批量处理能力
- 命令行友好，便于调试
- 配置驱动，易于扩展

缺点：
- 需要重构现有脚本

### 方案 C：分层设计

```
仿真引擎层（核心逻辑，与方法无关）
    ↓
方法适配层（参数映射、算法调用）
    ↓
接口层（CLI 脚本 / REST API）
```

- **仿真引擎**：样本生成、重复运行、结果汇总
- **方法适配**：每种方法的参数定义、算法调用方式
- **接口层**：CLI 用于预计算，API 用于实时

我倾向于 方案 B + 方案 C 的混合：

  1. 统一的核心仿真引擎（一个 Python
  模块）                               
    - 输入：方法ID、参数字典、重复次数
    - 输出：标准化的结果行（CSV 格式） 
    - 不关心是"预计算"还是"实时"       
  2. 两种调用方式复用同一个引擎：      
    - CLI 脚本：调用引擎 → 写入 chunk  
  文件
    - FastAPI：调用引擎 → 返回 JSON    

  这样改完后，加新方法只需要：
  - 在方法映射表加一行
  - 定义该方法特有的参数（如 MDM 的    
  offset）

  而不是复制 600 行代码再改几个变量名。

  关于变量命名，我觉得应该定一个"源头真
  理"：
  - 配置层（config.md）用什么名，所有层
  都用什么名
  - chunk 文件名、CSV
  列名、前端状态，全部通过映射表转换
