# chuchuzhao

> 技能版本：v1.1.0

产出一份用户能直接复制给他人或其他 AI 的上下文材料。以“需要写的写，不需要写的不写，详略得当”为标准，不追求少写、多写或固定压缩比例。接收者没有当前对话上下文，但并非没有通用知识；材料应补足其理解这件事所缺的背景。自包含意味着不依赖原上下文就能理解情况，不意味着复述全部已知信息，也不要求材料必须以提问结尾。

## 先判断接收者缺什么背景

根据用户指定的接收者判断知识起点。未指定时，以有一般知识、但完全没参与本项目的人或 AI 为对象。不要假定对方知道本地项目、特定文献中的方法、方法变体、内部简称或此前的决定；也不必从头讲授通用概念。

- **通常已知的知识**：简要点明即可；只有本次用法特殊、容易混淆或影响判断时才解释。
- **不提供就可能不知道的背景**：讲清对象是什么、基本做法是什么、它与当前问题有什么关系。必要时说明输入、关键机制和输出，不能只展开缩写或贴一个用途标签。
- **本项目才有的事实**：保留影响理解的动机、关键选择、已有结果和未决事项。结果说明比较对象与适用范围，避免只报百分比或内部指标名。
- **不影响理解和判断的细节**：不写。不能因为路径、配置、流水记录容易提取，就让它们占据篇幅。

先补理解主线所需的背景，再筛选支撑细节。详略由它对本次理解的作用决定，不由“是否技术内容”或“能否一句话说完”决定：关键机制可以多写几句，通用知识和无关操作经过可以完全略去。解释到接收者能够理解问题、提出有根据的意见为止；不要求每个名词都下定义。

例如，向无项目上下文的 AI 介绍 MDM，仅说“MDM 是一种参数估计方法”仍可能不够。若讨论涉及它的改进机制，可以交代：“这里的 MDM（最小差异法）根据排序样本构造多个尺度参数的伪估计，通过减小这些量之间的差异估计三参数 Weibull 分布的参数；后续方法在位置参数搜索中加入固定偏移量。当前研究保留求解结构，让偏移量随观测样本调整。”这说明了改进发生在哪里，无需接着列出全部求解公式、网络层数和文件名。具体解释只采用已知材料，不凭缩写猜测方法。

## 版本命名

需要产出可保存的 Markdown、报告或其他独立材料时，给材料一个可追踪的版本号，并把版本号放进文件名或标题；已有同名材料时沿用其版本序列，不另起一套编号。采用 `v主版本.次版本.修订版本`：内容结构、论证范围或结论发生实质变化时升主版本或次版本；只修正措辞、链接、格式或小错时升修订版本。日期用于说明生成时间，不替代版本号。若只是当前对话中的临时整理，不必为了形式强行编号。

每次生成新版本时，简要写明本次相对上一版改了什么；不得把未实际发生的版本历史补写出来。

## 首要边界：没明确说要问什么，就只整理

默认只整理背景、经过和现状。仅当用户明确给出此次要转交的问题，或明确指向前文某个要保留的问题时，才附上该问题。不确定用户想问什么时，采用只整理内容的方式，不猜测，也不追问。

用户描述困难、表达不满、提到某个卡点，或说“拿给别人看看”“让别人出出招”，都不等于已经提出了要转交的具体问题。可以如实描述这些情况，但不能将其转换成“我想问的是……”“请帮我判断……”“应该如何……”或隐含同样要求的陈述句。不要把当前 agent 想到的问题、历史讨论中的疑问或自己判断的核心矛盾自动当作用户此次的问题。

没有明确问题时，正文在情况说明结束处自然结束，不添加问题清单、求助结语、待填写的问题占位符，也不必写“用户尚未提出具体问题”。只有用户另外明确要求代拟问题时，才允许代拟；不能从调用本技能推断出这种授权。

## 两种用法

根据用户本次表达直接选择，不要求用户报模式名称，也不为选择模式追问。拿不准时采用第二种。

### 用户已说清楚要问什么

围绕这个问题筛选、归纳相关背景、经过和现状，将整理后的上下文与用户的问题放在同一份可复制正文中。问题默认保留原话；仅为脱离原对话后仍能读懂，补全有明确依据的指代或做最低限度的语句整理，保持原来的范围、开放程度与语气。

不要替用户解释“你真正想问的是”，不要添加隐含诉求、预设原因或推导出的子问题。用户问一个开放问题，就保留一个开放问题；用户自己列了多个问题，则保留其问题范围和层次。只有用户明确要求改写或拆解问题时才这样做。

### 用户只大概说明要提供哪些内容，或没有说清具体问题

按用户指定的主题或范围整理已知上下文，让接收者先了解相关情况。用户只说“整理一下项目背景和目前情况”，就交付这些内容，不强行寻找核心卡点、制造问题或添加“请你回答以下问题”。若同时给了宽泛求助，例如“想听听你的看法”，保持这种宽泛表达，不收窄为具体决策题。

## 保留提问空间

整理材料的权限不等于重新定义问题的权限。不要通过补充分析、引导性标题或结尾要求，暗中把开放问题改写成诊断题、选项题或执行任务。除非用户已经提出，不自行附加“请分析原因、比较方案、列出风险、给出验证步骤”等回答清单，也不规定回答结构、方案数量或优先考虑的方向。必要的背景解释用于理解事实，不能代替用户解释问题意图。

## 主次与详略

- 以用户明确的问题或大致提供范围为依据组织材料。不能直接把最近的报错、局部实现难点或操作记录当成整件事的核心，也不能把上下文整理擅自变成问题诊断。
- 正文先完整讲清范围内的主线：在做什么、为什么做、目前到了哪一步。用户涉及困难或求助时，再讲清相应情况和原问题。前几段就要让人建立整体理解，不要只加一句摘要，随后立即堆细节。
- 每个细节都问：没有它，对方是否还能理解对象、问题为何出现，以及现有结果意味着什么？若会留下理解断点，就按需要讲清；若不影响理解或判断，就省略。优先解释含义与关系，必要时才给原始细节，不能一味删减背景或堆积证据。
- 将多次尝试压缩成关键路线、结果及其暴露的问题，只保留改变现状或思路的转折。不逐项罗列所有尝试、成果、限制或未知。
- 默认省略文件路径、函数名、字段名、命令、日志、逐项测试数量和内部编号。确实影响本次判断的精确信息才保留；不要把向人请教方向写成要求对方接手实现或排错。
- 只有正文确实无法容纳、且有助于进一步判断的细节，才放在末尾的“补充信息（可跳过）”。正文必须能够独立成立；补充也要筛选，不能把删掉的流水账整体搬过去。没有必要就不设补充部分。

例如，用户问“这个项目接下来该怎么走？”，可先概括材料支持的现状：“目前流程已经能跑通，但关键环节仍依赖人工判断。”然后保留用户的原问题。不要擅自改成“应该继续自动化还是缩小范围？请分别分析成本、风险和验证步骤”，因为这替用户设定了选项并限制了回答空间。

## 整理原则

- 直接整理已知信息，不发起澄清访谈，不等待用户补充或确认。会影响理解但尚不清楚的内容明确写为“未知”或“尚未验证”；信息少时也交付可用正文，不用空模板代替。
- 优先使用当前对话和用户提供的材料。问题涉及项目且已有明确线索时，可定向读取必要的相关文件以补足事实；不为写总结开展全项目审计、广泛检索或新的实验。无法读取的材料不假装读过。
- 围绕用户的问题或提供范围筛选信息，保留解释现状所需的关键经过、选择原因和约束，省略无关对话与操作流水。若范围也未明确，依据当前讨论主题整理并简短点明范围，不擅自选择某个卡点作为用户的问题。
- 区分已确认事实、用户陈述或偏好、当前 agent 的推测以及待验证方案。计划、建议和局部测试通过不能写成已实现或整体成功；先后发生不等于存在因果关系。
- 对保留的关键尝试讲清实际结果及仍未解决的问题。已被后续证据修正的判断不能继续作为当前事实；影响判断且无法消解的冲突如实注明。
- 用外行于本项目的人能理解的语言解释必要概念，优先描述对象的用途及关系，少用内部名称。关键证据通常概括为事实及其意义；只有精确措辞影响判断时才摘录。不能用本地路径、内部链接或“见上文”代替说明。
- 保留用户的目标和立场，不把 agent 的建议改写成用户已作出的决定。允许接收者重新审视问题设定，避免用预设诊断或单一方案引导答案。

## 输出

默认使用用户当前使用的语言，以用户向他人介绍情况的口吻，直接给出一份可复制的正文；仅在用户有明确提问时保留其求助表达。不附带整理过程说明；用户要求文件时再保存文件。优先用几段连贯文字讲清主要内容，篇幅随所需背景的复杂度调整，不随原始材料数量增长；不设机械字数限制。

推荐的叙述顺序是：简要交代正在做什么及目的，说明范围内的关键经过和现状，保留相关的必要约束。用户明确给出此次要转交的问题时，将原问题清楚放在正文中；其余情况整理完相关内容即结束。可使用简短标题，不强制填满固定栏目，不把每一类信息都展开成清单。

输出前逐一检查正文里的提问和对接收者的请求：能否对应到用户明确指定要转交的原话？无法对应且用户未授权代拟的，删除。不要因为正文没有问题或求助结尾，就认为输出不完整。

交付前，假设接收者只看得到这份材料，分别检查背景是否缺失、细节是否过量：

- 对方能否理解关键对象的基本做法、当前改动的位置与目的，而不必猜测专有名词？需要哪些本项目背景才能正确理解结果，是否已交代？
- 是否反复解释接收者通常知道的知识，却漏掉本项目独有的前提？是否列了很多数值和操作，却没有解释它们与问题的关系？
- 每段保留的信息是否帮助对方理解或判断？该补的补，该展开的展开，无关的删；不按字数或压缩比例验收。
- 跳过补充，正文是否仍能独立理解？是否擅自添加了问题、动机、解释、选项或回答要求，改变了用户原问题的开放程度？有则修正。

最后检查隐含指代与事实边界。缺失信息如实保留，不靠编造补齐。
